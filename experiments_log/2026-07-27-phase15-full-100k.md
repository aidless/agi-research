## 3. SlotMonitor calibration

\[A] SlotMonitor trained (AUROC ~0.989)\ -- consistent with commit
8d89ca0 (SlotMonitor AUROC 0.989 vs raw 0.796, +0.193 breakthrough).

However in practice the monitor rarely crossed the 0.5 threshold during
eval (only 4 gates across 5 episodes, all in ep0). This suggests:
- AUROC measures ranking quality, not calibration at a threshold.
- With more diverse training rollouts (we use 200) the failure-prob
  distribution is heavily skewed toward 0, so even when gate threshold
  is 0.5 the monitor almost never fires.

## 4. Q-function with CQL

Trained on the same 200 rollouts. The single gate fire in ep0 was a
**bad** Q action (gated -27 vs ungated +203). This is a known CQL
weakness: CQL penalizes OOD actions but the value of in-distribution
"safe" actions can be miscalibrated. With 200 episodes Q has limited
coverage.

## 5. Verifier

\[E] Verifier ready with 3 rules\ - all three LTL rules evaluated per
episode. With 100K-trained PPO:
- 5/5 episodes: ALWAYS angle_below(1.0) freq=1.0 (always satisfied)
- 5/5 episodes: EVENTUALLY velocity_below(0.3) freq=1.0 (eventually satisfied)
- 4/5 episodes: ALWAYS (landed IMPLIES in_pad) freq=1.0 (always satisfied; ep0 fails)

The verifier is a hard constraint check. It does not influence the
action; it only logs violations. To make it active in the policy loop
would require Project E Phase 2 work (shielding / constrained RL).

## 6. Why the previous Codex task kept getting interrupted

This run was the v0.2.0 milestone. The previous Codex session kept
failing because:

1. **Synchronous shell_command**: \shell_command\ has a default 10s
   timeout. 100K PPO + 200 train + 5 eval takes ~7 minutes.
2. **Duplicate background processes**: when previous Codex tasks were
   interrupted mid-run, the child Python processes (PID 24412, 24896)
   were not cleaned up. When a new session launched another 100K run,
   3 instances competed for CPU and 1.5 GB of RAM, making each 3-5x slower.
3. **No progress visibility**: without log tail checks, Codex had no way
   to know whether the run was making progress or hung.

The fix used in this session:
1. Launch via \Start-Process -WindowStyle Hidden\, redirect output to a
   timestamped log file, save PID to a .pid file.
2. On resume, inspect \Get-CimInstance Win32_Process\ for old orphans
   and kill them.
3. Poll log size + process CPU instead of waiting synchronously.
4. Continue with non-blocking prep work (PROGRESS.md updates, etc.)
   while the experiment runs.

This is documented in PROGRESS.md "Infrastructure" section.
