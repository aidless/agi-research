## 3. Why composable still fails

Possible reasons (in order of likelihood):
1. **ENWI's scene generator uses physics-accurate equations**:
   - free_fall: y(t) = y0 + v0*t + 0.5*g*t^2
   - collision: momentum conservation m1*v1 + m2*v2 = m1*v1' + m2*v2'
   - friction: kinematic friction
   - inertia: F = m*a
   Our scene generator uses simple linear perturbations
   (y -= 0.5, vel *= 0.5, etc.) which is too easy to memorize

2. **More training data needed**: ENWI uses 250K scenes per epoch,
   we use 1000

3. **Different module architectures**: minor differences in our
   port may matter

4. **100 epochs is not enough**: ENWI uses 2000 epochs (20x ours)

## 4. Y1 work to truly replicate

To actually replicate ENWI's 94% improvement:
1. Physics-accurate scene generator (closed-form equations)
2. 2000+ epochs training
3. 250K scenes per epoch
4. Match ENWI's exact module architectures (network shape, gate net)

Without these, composable physics may not help on simple synthetic
data — monolithic can memorize the simple patterns.

## 5. Honest replication status

ENWI's 94.22% improvement claim: NOT replicated at our scale.

This is a meaningful negative result because:
- Our port is architecturally correct
- The smoke + 100-epoch tests both show composable 1.9-3.5x worse
- ENWI's headline result requires significantly more compute and
  better synthetic data

**For our 5-year program**: ENWI's framework is still valuable as
theoretical foundation, but composable physics is not a quick win
for Project C. Better focus on:
- Slot attention (differentiable logic, ENWI's OCM maps well)
- Active inference (Project A)
- DLR (Project E, we ported successfully)
- Real self-improvement loop (not just gating)
